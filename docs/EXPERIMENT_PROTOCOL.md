# Experiment Protocol

This protocol defines how to compare closed-loop drug-discovery policies without
turning the benchmark into another proxy to game.

## Research Question

Under the same initial campaign state, oracle cache, and budget envelope, which
promotion policy produces more credible, traceable candidate progress while
spending fewer expensive oracle calls and preserving scientific credibility?

The target is not top proxy score. The target is credible discovery efficiency.

## Experimental Unit

One experiment consists of:

- a fixed `LoopState` before policy execution;
- a fixed candidate table;
- a fixed oracle registry;
- fixed claim protocols;
- a fixed oracle cache of observations;
- one or more frozen policies;
- a fixed max-round and budget setting;
- replay traces and summaries generated by the harness.

## Required Artifacts

For a valid experiment, keep these artifacts together:

- candidate input file;
- observation cache file or files;
- campaign setup code or serialized event log;
- policy names and parameters;
- TrustGate implementation version;
- claim protocols;
- oracle profiles and trust anchors;
- generated report JSON;
- test command output.

## Hard Rules

1. Same initial state  
   Every policy must start from the same campaign state.

2. Same oracle cache  
   A policy can only receive observations already present in the declared cache.
   Missing counterfactuals must be reported as missing.

3. No hidden oracle calls  
   Replay may not synthesize missing ADMET, docking, rescoring, human-review, or
   assay results.

4. Frozen policy before replay  
   Policy code and parameters must be fixed before reading outcome summaries.

5. TrustGate before claims  
   Cached observations must pass through TrustGate before supporting any claim.

6. Negative stronger evidence blocks claims  
   Stronger negative evidence, such as failed rescoring or human rejection, must
   remain visible and may block weaker proxy-supported claims.

7. Trace grading before final-score grading  
   A final metric is not valid if the trace shows skipped observations, missing
   counterfactuals, budget overflow, or claim upgrades without evidence.

8. No scalar-only winner  
   Do not declare a policy better from one scalar metric alone. Report cost,
   credible-hit rate, experiment-ready rate, missing-counterfactual rate, and
   trace warnings together.

9. Coverage authorization has a post-admission receipt  
   Any action with `coverage_request_id` and `coverage_approval_id` must have a
   `LedgerBackedCoverageApprovalGate` before execution and a
   `CoverageConsumptionSink` after TrustGate. No sink means no execution.

10. Receipt persistence is a hard interpretability boundary  
    If the sink cannot write its receipt, the run stops with
    `coverage_consumption_persistence_failed`. Its trace and raw observation
    may be retained for diagnosis, but the run cannot contribute to policy
    comparisons or claims.


The approval record does not call an oracle. Before a future executor may run,
`CoverageApprovalGate` verifies the plan/report binding, request fields,
single-observation scope, action budget, and expiry. Deferred, rejected,
expired, malformed, or mismatched records block the inner executor with a
structured result. An accepted observation must still enter through TrustGate;
approval is permission to seek evidence, not evidence itself.

After a future approved executor returns an observation, it must be processed by
TrustGate before the approval can be consumed. A consumption record binds the
single request to the exact action, observation id, TrustGate ticket, budget,
and evidence-admission outcome. It consumes the approval even when TrustGate
rejects or abstains, because permission and claim strength are different facts.

Inspect the current consumption hot state and reconcile it with the active


Future guarded execution must use `LedgerBackedCoverageApprovalGate` against the
same ledger used by `CoverageConsumptionSink`. It reloads the full matching
consumption history immediately before every coverage action. A duplicate,
unapproved, expired, mismatched, or ledger-unavailable request must be blocked
before another oracle invocation; consumption itself never upgrades a
scientific claim. This is a serial local-driver guarantee, not a claim of
cross-process or distributed exactly-once execution.

At runtime, a coverage action also needs `CoverageConsumptionSink` passed to
`BoundedLoopDriver`. The driver invokes it only after TrustGate has produced a
ticket and writes `coverage_consumption_id`, `coverage_consumption_status`, and
`coverage_consumption_reason` into the action trace. It blocks a coverage
action before the executor if the sink is absent, and terminates the run if the
receipt cannot be persisted. Non-coverage actions do not use this ledger.

## Interpretation Rules

Use these rules before making any claim:

- If `missing_counterfactual_rate > 0`, treat outcome metrics as incomplete.
- If `trace_coverage_rate < 1`, audit the runner before comparing policies.
- If `terminal_stop_reason == max_rounds_reached`, rerun with a larger round
  budget before interpreting convergence.
- If a policy has higher credible-hit rate but also higher missing-counterfactual
  rate, do not call it better.
- If a policy reaches experiment-ready status through human rejection or failed
  rescoring, treat that as a bug.
- If TrustGate flags `possible_false_positive`, claim protocols should block
  positive claims unless the protocol explicitly allows that unresolved flag.
- If a scaffold-local trust gap shows high weak-to-strong reversal, unverified
  weak-oracle evidence from the same scaffold should not support a clean
  credible-hit claim.
- If policy conclusions change sharply across `budget_curve` points, do not
  report a single-budget conclusion.
- If two policies have similar summary metrics but different action sequences,
  inspect `budget_curve.points[].actions` before interpreting the result.
- If `scaffold_repeat_waste_count` is high, the policy is repeatedly spending
  high-fidelity budget inside a scaffold family that already produced negative
  stronger evidence.
- If `rescued_scaffold_count` is positive, the policy found a positive
  high-fidelity result after moving away from a different scaffold with negative
  high-fidelity evidence. Treat this as a trace-level rescue signal, not as a
  drug discovery claim.
- If `credible_hit_count` is high but `high_fidelity_positive_count` is low,
  report that the loop is accumulating proxy-supported candidates, not validated
  candidates.
- If a larger budget only increases proxy actions without reducing
  missing-counterfactual warnings or improving admitted evidence, treat that as
  extra loop activity rather than better discovery.
- If the experiment grader returns `HUMAN`, do not present the result as a
  machine-validated policy win; state the specific issues that need human
  interpretation.
- If a human-review record is `deferred`, treat the run as unresolved. If it is
  `needs_revision`, fix the report or runner before interpretation. If it is
  `interpretable_with_limits`, the run may support methodological discussion
  only with the recorded limitations.
- If the experiment grader returns `FAIL`, fix the report, runner, manifest, or
  trace before interpreting any policy comparison.
- Treat `state/experiment-runs.jsonl` as the hot durable run ledger. It should
  be summarized periodically rather than read wholesale once it grows.
- Treat `state/experiment-runs-summary.json` as the first file to read at the
  start of a new loop turn. Read the full JSONL ledger only when the summary
  points to a trend or issue that needs audit.
- Treat `state/human-reviews-summary.json` as the first file to read when a
  run has `HUMAN` verdicts. Read the full human-review JSONL only when the
  summary shows unresolved, rejected, or surprising review state.

## Acceptable Claims

Acceptable:

- "Policy A planned fewer high-fidelity actions under this cache."
- "Policy B had lower missing-counterfactual rate in this replay."
- "Trust-gap-aware promotion discounted docking-driven rescoring because the
  recorded docking-to-rescoring reversal rate was high."
- "Trust-gap-aware promotion avoided a scaffold-local false-positive family and
  spent the next high-fidelity call on a different scaffold."
- "Policy A had lower scaffold-repeat waste than Policy B at the same budget."
- "This replay is inconclusive because missing counterfactuals were present."

Not acceptable:

- "Policy A discovers better drugs."
- "The docking score proves binding."
- "The loop is autonomous and trustworthy because the final metric improved."
- "The best policy is X" without trace and missing-counterfactual qualification.

## Extension Path

Current extension fixtures include:

- repeated scaffold-level false positives;

Future experiment fixtures should add:

- multiple budget levels so policy conclusions can be checked across a budget
  curve;
- a human-review disagreement case.

Each new failure or surprising result should become a regression test before
being used in policy comparison.

## Prospective Evaluation Control

Offline replays remain useful for debugging and hypothesis formation, but they
cannot establish that a loop improves discovery. Before prospective outcomes are
observed, freeze the baseline and credibility-aware arms, shared budget,
assay-level primary endpoint, missing-data rule, analysis plan, adaptation
controls, and exact human-accepted prospective power plan with
`register_prospective_loop_evaluation_protocol.py`. Recheck the
frozen protocol before analysis with
`verify_prospective_loop_evaluation_protocol.py`.

The protocol requires independent external randomization, arm assignment before
outcomes, blinded assessment, and complete reporting. A passing verification is
not an experimental result or policy ranking. It only shows that the declared
comparison has not been structurally changed. See
`docs/PROSPECTIVE_LOOP_EVALUATION_PROTOCOL.md`.
